# 8.5 Verify inclusive accessibility across the service

## Story

As a **person using assistive technology or a mobile device**, I want content,
structure and behavior accessible, so that I can complete the same civic task.

## Acceptance Criteria

1. Critical report, tracking, consent and legal flows are audited against WCAG 2.1
   AA with keyboard, focus, semantics, contrast and reduced-motion evidence.
2. Errors, validation, dialogs, cookie preferences and dynamic Lit/Alpine updates
   are announced and operable without a pointer.
3. Every finding has severity, affected locale/component, owner and retest evidence.
4. The result is connected to the existing accessibility declaration gate.

## Tasks / Subtasks

- [ ] Extend the existing critical-flow audit matrix (AC: #1)
- [ ] Test dynamic behavior and consent interactions (AC: #2)
- [ ] Record and retest findings (AC: #3)
- [ ] Link the candidate result to the declaration/release gate (AC: #4)

## Dev Notes

- The guide requires accessibility of appearance, content, structure and behavior;
  this is broader than visual parity. [Source: bmad-output/research-report.md#Designers Italia: findings relevant to FixCity]
- Existing WCAG and accessibility-statement stories remain authoritative and must
  not be duplicated. [Source: bmad-output/stories/6.1.accessibility-candidate.story.md]

## Testing

- **Approach:** automated axe/WCAG scan plus manual keyboard, screen-reader and
  mobile checks on the candidate environment.
- **Scenarios:** all supported locales, consent modal, form errors, map fallback,
  legal incomplete state and reduced motion.

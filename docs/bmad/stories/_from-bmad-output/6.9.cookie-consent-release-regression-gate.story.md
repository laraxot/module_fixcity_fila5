# 6.9 Cookie consent release regression gate

## Story

As a **release engineer**, I want automated cookie and network regression gates,
so that a future change cannot silently reintroduce tracking, duplicate banners
or untranslated legal content.

## Acceptance Criteria

1. A clean browser context fails the gate if any cookie outside the approved
   inventory is emitted on public pages before consent.
2. The gate verifies exactly one banner, localized policy links and the full
   consent value matrix after each action.
3. Network assertions fail on unapproved analytics/marketing/third-party
   requests before consent and pass only for approved categories afterward.
4. Evidence is attached to the release candidate and the failure explains the
   offending cookie/request/page.

## Tasks / Subtasks

- [ ] Define approved inventory fixture per candidate tenant (AC: #1)
- [ ] Implement clean-context browser matrix (AC: #1, #2)
- [ ] Capture and classify network requests by consent category (AC: #3)
- [ ] Publish actionable evidence in the release gate (AC: #4)

## Dev Notes

- Release evidence is a MUST requirement, not a local HTTP-200 claim.
  [Source: prd.md#FR-018]
- Reliability and operability require observable release behavior.
  [Source: prd.md#NFR-006]
- The known technical inventory is a starting fixture only; owner-approved
  candidate data supersedes it. [Source: 6.4.cookie-policy-localized-inventory.story.md]

## Testing

- **Approach:** Playwright end-to-end with network interception and CI artifact upload.
- **Key scenarios:** first visit, necessary-only, all-consent, reload, revoke,
  all public locales and representative public routes.
- **Per-AC verification:** AC #1 → cookie allowlist; AC #2 → DOM/value matrix;
  AC #3 → request classification; AC #4 → failure artifact assertion.
- **Fixtures / mocks:** approved cookie manifest and provider stubs.
- **Edge cases:** service worker, cached third-party resource, redirects,
  malformed consent and error pages.

# 9.1 Prepare the production-like candidate environment
## Story
As an **operations owner**, I want a reproducible isolated candidate, so that release evidence reflects the environment that will go online.
## Acceptance Criteria
1. The candidate has documented runtime versions, HTTPS, domains/locales, tenant config, database, storage, queues, mail and secrets sources.
2. Deployment, migration, cache/build and health checks complete reproducibly without mutating historical migrations or committed secrets.
3. Rollback to the previous candidate is rehearsed, including failed migration/deploy and asset mismatch.
4. The manifest records commit, environment, timestamps, data classification and known limitations.
## Tasks / Subtasks
- [ ] Define candidate manifest and prerequisites (AC: #1, #4)
- [ ] Execute deployment/migration/health rehearsal (AC: #2)
- [ ] Rehearse rollback and capture evidence (AC: #3)
## Dev Notes
- Release completion requires candidate evidence, not source presence. [Source: bmad-output/completion-gap-analysis.md#What is missing for completion?]
- Migrations are forward-only and tenant/infrastructure credentials require owner/Ops approval. [Source: bmad-output/architecture.md#ADR-005 — Data and migrations] [Source: bmad-output/project-context.md#Core Constraints]
## Testing
- **Approach:** deployment integration, health checks and rollback drill.
- **Key scenarios:** clean deploy, retry, failed migration, expired asset and rollback.
- **Per-AC:** inspect manifest, logs and rollback result on the named candidate.
- **Fixtures / mocks:** synthetic tenant/data; no production personal data.
- **Edge cases:** queue unavailable, storage permission and locale fallback.
